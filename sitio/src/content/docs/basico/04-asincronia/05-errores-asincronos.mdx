## Objetivos

- Explicar qué pasa con una promesa rechazada que nadie atiende.
- Detectar un `await` olvidado por sus síntomas.
- Explicar por qué `try`/`catch` no atrapa errores lanzados dentro de un callback.
- Reintentar una operación que falla de forma pasajera.

## Explicación

### Rechazos sin atender

Una promesa rechazada que no tiene `catch` ni `await` que la atienda es un **rechazo sin
atender** (_unhandled rejection_). Node lo trata igual que un error síncrono sin capturar:
imprime el error y **termina el programa con código 1**. Es a propósito: un error ignorado en
un servidor puede dejar datos a medias sin que nadie se entere.

La regla: **toda promesa debe terminar en un `await` (dentro de un `try` si quieres manejar el
error) o en un `.catch()`**.

### El `await` olvidado

Es el error asíncrono más común, y no siempre truena. Sus síntomas:

- Ves `Promise { <pending> }` donde esperabas un valor.
- Una propiedad sale `undefined` (`tarea.titulo` cuando `tarea` es una promesa).
- Una comparación da un resultado raro: `if (await existe())` no es lo mismo que
  `if (existe())`, que siempre es verdadero, porque una promesa es un objeto.
- El `catch` no atrapa el error: `return promesa` dentro de un `try` devuelve la promesa antes
  de que se rechace. Usa `return await promesa`.

### Errores dentro de callbacks

`try`/`catch` solo atrapa errores que ocurren **mientras** se ejecuta el bloque `try`. Un
callback de `setTimeout` (o de cualquier API de callbacks) se ejecuta después, cuando el `try`
ya terminó. Por eso los callbacks usan la convención error-first en lugar de `throw`: el error
**viaja como argumento**. Con promesas y `await` este problema desaparece, otra razón para
preferirlos.

### Reintentar

Algunos errores son pasajeros: la red falló un instante, el servidor estaba ocupado. Para
esos, reintentar después de una breve espera suele funcionar. Solo reintenta lo que puede
salir bien la segunda vez: un "usuario no existe" va a fallar igual.

<Aside type="caution" title="Último recurso: process.on('unhandledRejection')">
  Puedes registrar una función que se ejecute ante cualquier rechazo sin atender, por ejemplo
  para escribir un log antes de salir. No la uses para ignorar errores: si llegó ahí, tu código
  tiene un `await` o un `catch` faltante. Lo verás con más detalle en el módulo 20.
</Aside>

## Errores comunes

**El programa termina con un error y la pila menciona una función `async`, sin decir quién la
llamó.** Es un rechazo sin atender. Busca dónde se llama esa función sin `await` ni `.catch()`.

**`Promise { <pending> }` o `undefined` donde esperabas un valor.** Falta un `await`.

**`Promise { <rejected> Error: ... }` al imprimir algo.** Imprimiste una promesa ya rechazada
en lugar de esperarla. Ponle `await` dentro de un `try`.

**El error aparece dos veces, o se registra y además truena.** Atrapaste el error en un
`catch`, lo imprimiste y lo volviste a lanzar, y alguien más arriba también lo imprime. Decide
un solo lugar para reportarlo; en los demás, envuélvelo con `cause` o déjalo pasar.
